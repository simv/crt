## Summary
The agent's F-27 step-5 proposal — the restatement, `Proposed definition of done:`, the checklist, the fixed closing line — is the longest bubble in the thread, and the closing line is repeated by the Accept bar right under it. When a turn ends on the closing line, fold that bubble: the one-paragraph restatement (clamped to three lines) and a `▸ Definition of done · N items` pill; click to unfold the whole proposal in place, minus the closing line. The summary is a deterministic parse (`summarizeProposal`, pure, unit-tested) of what the agent already writes — no model, no extra call; the intake skill's step 4 states the proposal's shape so the parse is right for every provider. The Accept bar and its rule are unchanged. `docs/PRD-chat.md` §5.2, §5.3, F-120, N-29, N-30.

Keep the rest of step 4 (the wait, the edit loop, quick-note mode) word for word. `claude plugin validate ./plugin` green.
2. **`packages/overlay/src/proposal.ts`** (new, framework-free, no DOM): `export interface ProposalSummary { lead: string; items: string[]; body: string }` and `export function summarizeProposal(text: string): ProposalSummary` per PRD-chat §5.2 — `body` = `text` with the closing line removed (the same tolerances as `endsWithAcceptLine`: markdown emphasis, curly quotes, trailing whitespace; export the normaliser from `chat.ts` or move both helpers into `proposal.ts` and re-export from `chat.ts` so `accept-line.test.ts` keeps its import); `lead` = the first paragraph of `body` that is not a heading, a list item, a fence or blank (paragraph = lines up to a blank line, joined with a space), else the first non-blank line, else `""`; `items` = every `- [ ]` / `- [x]` / `- ` / `* ` / `1.` list item text in `body`, in order, boxes and markers stripped. No rendering here.
3. **Panel** (`chat.ts`): keep every assistant message's full text in `this.texts` (already there). On `assistant_end` for a message, and on `result` for the current `lastMessageId` (whichever comes first; idempotent), if `endsWithAcceptLine(text)`, render the bubble as a **proposal**: `el.classList.add("proposal")`, `innerHTML` = `<div class="lead">` + `inline(lead)` clamped to three lines by CSS while folded + `fold("Definition of done · N items" | "Full proposal" when N = 0, body)` where the fold body is `renderMarkdown(body)` and unfolding removes the clamp on the lead (`.proposal[data-open] .lead`). Any later `text` delta for the same message (should not happen after `assistant_end`) re-renders verbatim and the fold is re-applied at the next end. Messages that do not end on the line are never folded; `renderAccept()` is unchanged and still reads `this.texts` (not the DOM). `CHAT_CSS` gains `.msg.assistant.proposal .lead` (clamp) and the assistant-side `.fold-pill` colour if M25 has not landed it.

## Notes
Read `docs/PRD-chat.md` §5.2, §5.3, §11, §12 and §13 first. Decisions already taken: the summary is the agent's own restatement plus a count, no model; the trigger is the existing closing line, unchanged; the closing line is not rendered inside a folded proposal (the Accept bar is its UI); folded by default, no persistence; one `fold()` for both bubbles, no new colour tokens. A proposal without a list still folds with `▸ Full proposal` (§12 rule 1) — do not widen the parse to guess items from prose. If a provider emits `text` then `result` with no `assistant_end`, the `result` path must fold (§12 rule 2). The Accept bar's rule must keep reading `this.texts`, not the rendered DOM, or a folded bubble would hide the line from it. M25 (CRT-0030) folds the first user bubble; coordinate on `fold()` and the CSS rows — whichever lands first owns them.
